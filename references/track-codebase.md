# 代码库课程（codebase）

> 何时阅读：输入是 repo、源码、当前代码库、GitHub 链接、"这个代码库"时，写 `data.js` 前阅读。普通课程不读本文件。

## 输入

- 用户给 GitHub 链接时，先克隆仓库再分析。
- 用户说"这个代码库"或"当前代码"时，使用当前工作目录。
- 不要要求用户解释产品。自己从 README、入口文件、UI 和主要模块判断项目做什么。

## 必须读取

README / 入口文件 / UI 或 CLI 入口 / 主要模块 / 数据层 / API 或外部服务 / 测试或示例 / 真实代码片段。

## 必须提取

- 项目做什么
- 一条核心用户路径
- 主要角色：组件、服务、模块、脚本、数据层
- 关键 API、数据流和通信模式
- 技术栈以及每部分作用
- 真实代码片段
- 常见错误和调试入口
- sources 文件路径和行号

## 输出约束

```text
COURSE.profile = "codebase"
COURSE.style   = "default"    // 缺省；另一套是 "apple-blue"
```

- 展示形态：continuous 顶部滚动，不显示完成进度，顶部细进度条跟随滚动，圆点根据滚动位置 active/visited。
- 优先使用代码相关 block（`code-translation` / `actor-chat` / `flow` / `architecture` / `debug-case`）。
- 推荐写完整 `COURSE.context`（`title` / `path` / `summary` / `tags`）。
- 每节尽量包含真实代码片段、互动元素、应用型测验和代码来源。

## 受众

面向 vibe coder：他们用自然语言指挥 AI 编码工具，但没有系统读过代码。

课程要让他们能看懂项目结构、更准确地指挥 AI、发现 AI 把逻辑放错地方、在 AI 卡住时知道从哪里查、和工程师讨论架构时不迷路、学会能写进 prompt 的技术词汇。

## 怎么教

### 展示，而非讲述

课程应该像信息图，而不是教科书：

- 每节至少一半内容应该是视觉或互动 block。
- 3 个以上项目不要写成长列表，改成 `list-block`。
- 解释代码不要写段落，改成 `code-translation`。
- 解释组件通信不要写段落，改成 `actor-chat` 或 `flow`。
- 解释文件职责不要写段落，改成 `architecture` 或 `debug-case`。

### 代码 ↔ 自然语言解释

最重要的教学元素。每节课至少一个 `code-translation`，左侧真实代码，右侧白话中文解释。

- 太长就选自然短小的片段，不要改写。
- 解释说"为什么这么写"，不只说"它是什么"，并帮助学习者以后更准确地指挥 AI。

### 先隐喻，后代码

用日常隐喻建立直觉，然后立刻落回真实代码。不要重复同一个隐喻，不要默认用"餐厅"解释所有东西。

### 通过追踪来学习

从用户已经见过的动作开始追踪：

```text
你点击这个按钮后，数据先进入 A，再由 B 处理，最后 C 更新界面。
```

第一节从一个具体用户操作开始，再追踪背后的代码。

### 给组件角色感

主要组件不是图上的方框，而是故事里的角色。用 `actor-chat` 让它们说话：前端问后端要数据、后端问数据库查记录、缓存提醒"我已经有这个结果"。

### 术语必须解释

技术术语第一次出现时都要解释：API、JSON、DOM、CLI、SDK、缓存、函数、变量、模块、组件、状态、数据库、队列、认证、中间件、构建、打包、入口点、环境变量，以及学习者可能不知道的软件或服务名称。词汇本身就是课程目标之一。

### 测验考应用，不考记忆

优先题型：调试场景（先查哪里）、架构决策（放哪一层）、追踪练习（数据路径）、AI 指挥（怎么提示 AI 改）。避免"API 是什么缩写""哪个文件处理 X"这类记忆题。

### 每节课的最低内容

每节课至少：`goal` / 2-4 个核心内容 block / 一个真实代码或架构相关 block / `flashcards` / `quiz` / `sources`。

整门课至少出现：`code-translation` / `actor-chat` / `flow` / `architecture` 或 `debug-case`。

### 推荐学习曲线

| 位置 | 目的 |
|---|---|
| 1 | 项目做什么，一次真实操作如何发生 |
| 2 | 认识主要角色 |
| 3 | 数据怎么流动 |
| 4 | 外部世界、依赖、成本和失败点 |
| 5 | 关键模式，学会给 AI 更精确的指令 |
| 6 | 出错时怎么查 |
| 总复习 | 综合 |

根据代码库调整，不要机械套模板。

## 代码相关 block 怎么用

block 结构见 `schema.md`，这里讲什么时候用哪个。

- 只写 block 数据，不写 DOM、内联 `<style>`、内联 `<script>`。
- 当前 runtime 不支持的互动，不要临时塞 HTML，记录为后续扩展。

- **`code-translation`**：把一段真实代码讲给非技术学习者。`explanation` 每项贴近代码中的一小段。
- **`actor-chat`**：把组件通信讲成对话。适合前端和后端、控制器和服务、Agent 和工具、缓存/数据库/队列等角色协作。
- **`flow`**：展示数据如何一步步移动。每一步只讲一个动作，文案要让非技术学习者能追上。
- **`architecture`**：展示主要角色和依赖关系。适合第 2 节认识角色、总复习、解释新功能应该放在哪里。
- **`debug-case`**：建立调试直觉。适合用户反馈功能坏了、数据不刷新、API 失败、构建失败、AI 反复改错地方。
- **`ai-dialog`**：展示学习者如何和 AI 沟通，教学习者写更好的 prompt。prompt 要具体到文件、角色、数据流或失败症状，不写泛泛的"帮我优化代码"。
